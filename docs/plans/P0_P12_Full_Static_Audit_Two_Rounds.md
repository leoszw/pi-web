## Executive conclusion

P0-P12 is coherent as a deterministic/mock-backed control-plane implementation, but the cumulative branch is **not production-ready** and should not be merged/promoted as a production control plane before the findings below are addressed and command-level verification is available.

The audit found no evidence of:

- real MySQL connection or DML execution;
- browser exposure of Approval Token in Mutation Center;
- arbitrary SQL console in Sandbox;
- automatic Golden promotion in P12;
- browser-side mutation commit bypass;
- deliberate raw HTML rendering in the reviewed UI action path.

The primary findings are cross-cutting authorization / trust-boundary issues rather than individual P12 feature defects.

# Round 1 — Architecture / contract / state-machine review

## R1-HIGH-01 — Coding WebSocket bridge is outside the Control Plane trust boundary

### Evidence

`server/src/bridge.ts` keeps `/ws` as a Coding Agent RPC passthrough. A WebSocket connection immediately creates an `RpcClient` and starts a `pi` child process. Apart from model-config writes being disabled in `control-plane` mode, ordinary command frames are forwarded to the coding RPC process.

The bridge does not receive the Control Plane `PrincipalProvider`, trusted project context, or the HTTP `allowedOrigins` set.

The Control Plane design explicitly requires:

- authenticated WebSocket upgrade;
- CSRF / Origin controls;
- RBAC for the management plane;
- Industry Agent operations to go Browser -> BFF -> Industry Agent API instead of bypassing the BFF.

### Risk

The Industry HTTP API can be carefully scoped while `/ws` remains a parallel execution channel. In a browser context this also leaves a cross-site WebSocket attack surface because the WebSocket `Origin` is not validated by `attachBridge`.

Binding to `127.0.0.1` reduces remote-network exposure, but does not eliminate browser-origin attacks against a local WebSocket service.

### Required remediation before production

At minimum:

1. apply the configured Origin allowlist to `/ws` upgrade/connection handling;
2. in `control-plane` mode require an authenticated principal for the upgrade;
3. explicitly decide whether non-config Coding RPC commands are allowed in control-plane mode;
4. if they remain allowed, keep the Coding Chat trust domain explicitly separate and document that it is not an Industry BFF authorization path;
5. add WebSocket payload/rate limits and security regression tests.

Severity: **HIGH**

## R1-HIGH-02 — Industry Conversation / Workspace API has no explicit RBAC guard

### Evidence

`server/src/industry/conversation-router.ts` receives `TrustedRequestContext`, but not `AuthPrincipal`, and contains no permission check before:

- creating conversations;
- reading conversations;
- sending messages;
- reading events;
- aborting;
- submitting UIAction interactions.

Project isolation is enforced by the mock client, but authorization effectively becomes "principal can select this project => principal can use Industry Workspace".

### Risk

This is weaker than the rest of the Control Plane, where sensitive feature routers have explicit permissions. Project membership and feature authorization are different concerns.

### Required remediation

Introduce an explicit workspace/conversation permission model, for example:

- `industry.workspace.read`;
- `industry.workspace.run` / `industry.workspace.interact`;
- or a deliberate single `industry.workspace` permission.

The router should receive the authenticated principal and enforce the permission before calling the client.

Severity: **HIGH**

## R1-MEDIUM-03 — P11 deterministic mock Release Gate is labeled as `source = PI`

### Evidence

`shared/industry/eval/p11.ts` restricts `UnifiedReleaseGate.source` to literal `'PI'`.

The P11 run/gate is currently generated by `server/src/industry/eval/mock-evaluation-client-p11.ts`, i.e. inside the pi-web deterministic mock adapter, while the corpus source correctly says `PHASE_11_MOCK_MANIFEST`.

The Unified Benchmark UI also describes the result as "the release gate returned by pi" and renders "PI Gate".

### Risk

This is a provenance/truthfulness issue. A simulated gate can be mistaken for an actual gate returned by the `pi` execution/policy plane.

This conflicts with the architecture rule that `pi` owns final Release Gate semantics.

### Required remediation

Model provenance explicitly, for example:

```text
source = MOCK_PI_ADAPTER | PI
```

and render the mock source clearly until a real `pi` EvaluationClient adapter is connected.

Do not allow a mock run to be represented as evidence that production `pi` returned PASS.

Severity: **MEDIUM** (governance-critical)

## R1-MEDIUM-04 — Control Plane production authentication/session stack is still mock-only

### Evidence

`server/src/industry/auth.ts` implements `MockPrincipalProvider` backed by `PI_WEB_MOCK_PRINCIPAL_JSON`.

The target design requires OIDC/SSO or trusted upstream authentication, Secure/HttpOnly/SameSite session handling, and authenticated WebSocket upgrades.

### Risk

The current branch is suitable for deterministic Control Plane development, not real multi-user deployment.

### Required remediation

Treat real authentication/session integration as a hard production prerequisite, not a later cosmetic adapter swap.

Severity: **MEDIUM in mock stage / HIGH production blocker**

---

## R1-MEDIUM-05 — Project authorization mock only models tenant + company filtering

### Evidence

`MockIndustryAgentClient.listAuthorizedProjects()` filters the configured project fixture using:

```text
project.tenantId === principal.tenantId
principal.companyIds.includes(project.companyId)
```

There is no per-user/per-role project membership in the mock model.

### Risk

This is acceptable only if the configured project fixture is itself considered the trusted pre-authorized project list. It must not be mistaken for a production project-ACL implementation.

### Required remediation

The real project authorization adapter must return resources already authorized for the current principal, with server-side project membership/role rules owned by the authoritative identity/domain layer.

Severity: **MEDIUM production integration blocker**

# Round 2 — Adversarial composition / security / provenance review

## R2-HIGH-01 — Design-required CSRF and Rate Limit layers are absent

### Evidence

The target design explicitly lists:

- CSRF;
- Origin;
- Request size;
- Rate Limit;
- authenticated WebSocket upgrade.

The cumulative server security implementation currently has Origin, redaction, and request-size utilities, but no CSRF middleware and no rate limiter in the P0-P12 diff.

### Risk

The current `MockPrincipalProvider` means cookie-session CSRF is not yet the active authentication model, so this is not a current localhost exploit by itself. However it becomes a hard blocker as soon as a real browser session/cookie authentication layer is introduced.

Rate limiting is also needed for expensive endpoints such as conversation messages, eval runs, sandbox runs, multimodal analysis metadata requests, and WebSocket process spawning.

### Required remediation

Add security middleware before real authentication/staging rollout:

- CSRF strategy appropriate to the final session architecture;
- per-principal / per-IP / per-route rate limiting;
- WebSocket connection/process-spawn quotas;
- tests for rejected cross-origin and excessive requests.

Severity: **HIGH production blocker**

---

## R2-MEDIUM-02 — Knowledge write permissions allow blind write/reingest without `knowledge.read`

### Evidence

`server/src/industry/knowledge-router.ts` requires only:

- `knowledge.upload` for uploads;
- `knowledge.reingest` for reingest.

Unlike later hardened areas (Runtime config, P12 feedback, Report download), it does not require the corresponding read permission in addition to write permission.

The adapter still validates trusted project/company/ACL values, so this does **not** create cross-project access, but a principal without `knowledge.read` can submit an upload or guess a same-project document ID and trigger reingest.

### Required remediation

Choose and document one authorization convention. Recommended:

```text
knowledge.admin
OR
knowledge.read + knowledge.upload
```

and:

```text
knowledge.admin
OR
knowledge.read + knowledge.reingest
```

If blind-write semantics are intentional, explicitly document and test that policy instead.

Severity: **MEDIUM**

---

## R2-MEDIUM-03 — Generic secret redaction is key-name-only

### Evidence

`server/src/security/redaction.ts` redacts object values only when their **key name** matches `apiKey`, `authorization`, `cookie`, `secret`, `password`, `token`, `dsn`, etc.

`models-config.ts` permits an arbitrary non-empty `baseUrl`, and Control Plane model-config reads use `redactModelsConfigForControlPlane()` -> `redactSecrets()` after removing `apiKey`.

Therefore credentials embedded in a non-sensitive-named string, e.g. a URL userinfo component, are not covered by the generic redactor.

Trace has stronger string-pattern redaction, but Model Config uses the generic key-based path.

### Required remediation

Add string-level credential/DSN/userinfo redaction to the shared server redaction layer, or validate/reject credential-bearing URLs before returning Model Config in control-plane mode.

Severity: **MEDIUM**

---

## R2-LOW-04 — Selected-project session map has no TTL/bound

### Evidence

`IndustryContextService` stores selected project IDs in an in-memory `Map` keyed by tenant/user/session and has no expiry or maximum size.

### Risk

In localhost mock operation this is negligible. In a real long-running multi-user service, stale session keys can accumulate.

### Required remediation

Use the real session store or bounded/TTL state when production auth is introduced.

Severity: **LOW / operational**

# Areas that passed both static rounds

The following reviewed boundaries remain internally consistent in the current deterministic/mock implementation:

## Mutation

- Browser confirm payload is restricted to digest + `explicitConfirmation=true`.
- `Idempotency-Key` is header-only.
- Approval Token is not part of the browser contract.
- Project scope comes from server context.
- reconciliation-required paths remain fail-closed.

## Trace / Audit

- Basic trace is the minimum permission.
- Debug, Prompt and Audit are separately gated.
- Retrieval Debug requires debug permission.
- Trace Store masks known secret forms.

## Report

- download requires read + download permission (or admin);
- request body must be empty;
- returned mock grant is an opaque artifact reference, not a filesystem path.

## Sandbox / Agent Loop

- browsers do not submit SQL/Python/queryId;
- server adapters validate budgets;
- write SQL / SELECT * / LOAD_FILE / system schema and Python capability scenarios are fail-closed in deterministic mock behavior;
- critical Agent Loop tool is blocked instead of executing a mutation.

## Runtime

- config edit requires read + edit (or admin);
- stale version validation/save is rejected;
- secret-like aliases are rejected;
- no P10 Promote/Manual-PASS endpoint exists.

## Unified Benchmark / P12 Golden governance

- Waiver does not mutate a FAIL gate to PASS;
- waived FAIL runs are not baseline eligible;
- P12 dataset versions are `REVIEWED` and `golden=false`;
- no P12 Make-Golden / Promote-to-Golden endpoint exists.

## Browser rendering

The reviewed UI Action Registry renders dynamic values as React text nodes and does not use `dangerouslySetInnerHTML` in the inspected path.
